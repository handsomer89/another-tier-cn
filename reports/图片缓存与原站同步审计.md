# 图片缓存与原站同步审计

审查日期：2026-10-16。审查基线：最新 `origin/main` 的 `2bdae73`，加本次尚未提交的图片快照优先与浏览器图片缓存修改。由独立子代理只读审查业务实现，并通过本地 Chromium 模拟原站更新；未请求推送、外部写入或部署。

## 结论

原站 API 正常且数据符合现有格式时，角色评级变化、新增角色和星导状态能在镜像的在线榜单及个人图鉴中更新。本次图片优先级和 Service Worker 只影响图片，不会把榜单 API 或图鉴目录固定在旧版本。

在线显示、仓库静态副本和图片快照各自有不同更新时机：

## 同步边界

1. **180 秒是缓存新鲜期，不是轮询间隔。** 榜单使用 TanStack Query 的 `staleTime:180*1e3`，没有为角色查询设置定时 `refetchInterval`。过期后通常由重新挂载、重新获焦或恢复联网等查询事件触发重新读取。持续留在前台的页面不会保证每三分钟自动更新。静态 HTML 先显示已部署的 SSR 快照，浏览器执行后再由查询结果更新；禁用 JavaScript 时只有静态版本。
2. **图鉴在初始化时读取在线目录。** 重新打开或刷新会重取两组 API；已打开的图鉴没有后台轮询。浏览器往返缓存恢复且已有目录时也不会自动重取（`assets/collection.js:428`）。导出使用本次页面的目录与导出开始时的状态，不单独重新请求角色列表（`assets/collection.js:390`、`assets/collection-export.js:207`）。
3. **新角色详情的站内点击和直接访问不同。** 本地模拟确认：榜单客户端路由跳转到新 `slug` 后，可读取 `/v1/characters/<slug>` 并显示详情；同一地址直接刷新在普通静态托管下返回 404，因为尚无 `c/<slug>/index.html`。仓库没有新增通用 404/SPA 路由兜底。GitHub Pages 存在此限制；Cloudflare 的最终表现取决于托管自身的回退规则。运行静态刷新并部署会补齐角色目录（`scripts/refresh-rankings.py:219`）。
4. **新增图片与同地址换图的处理不同。** 未收录的图片 URL 直接到 CDN；已收录 URL 使用本地内容哈希版本。浏览器 Cache Storage 不会定期检查原站换图。部署新 hash 后请求新 URL，Service Worker 写入成功会删除同路径旧版本（`image-cache-sw.js:18`）。旧标签页继续使用其加载时的 manifest，刷新后才读取新的资源关系。
5. **上游格式变动需要维护。** 当前枚举包含固定的评级、属性、武器等。原站引入未知枚举或改变必填字段，可能被校验拒绝并回退静态副本；此时不会把原站任意新格式直接显示（`assets/collection-catalog.js:3`、`:24`）。

## 浏览器缓存审查

- `image-cache-sw.js:31` 只拦截同源、当前站点 `mirror-images/` 路径、带 12 位十六进制 `v` 的 GET 图片；HTML、API、JSON 目录和个人记录不进入该缓存。
- 页面和导出共享版本化快照 URL；Service Worker 合并同 URL 并发加载，成功图片才写入，缓存最多 1,200 项。不可用/已清除/空间不足时仍可继续网络加载。
- `assets/image-fallback.js:51` 仅在安全上下文及浏览器支持时注册；首次打开尚未被控制前依赖浏览器 HTTP 缓存，后续访问可复用 Cache Storage。因此不能承诺所有浏览器都永久零流量。
- CDN 回退资源不写入这个 Service Worker 缓存，其浏览器 HTTP 缓存仍由 CDN 响应头决定。用户清理站点数据后需要重新加载图片。

## 维护方式

仅同步榜单和新角色，可运行原有增量流程：

```sh
python3 scripts/refresh-rankings.py
```

同时需要刷新同 URL 图片和仅详情变动时，运行：

```sh
python3 scripts/refresh-rankings.py --full-details --refresh-images
```

刷新成功后提交生成文件并按已有方式部署，静态副本、新角色直接访问及图片内容版本才会同步到托管站点。本报告没有执行全量外网刷新、推送或生产部署。
