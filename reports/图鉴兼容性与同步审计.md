## 发现并修复的问题

| 问题 | 影响 | 修复 |
| --- | --- | --- |
| 两个标签页用各自旧记录保存 | 后一次保存可能覆盖另一角色刚完成的修改 | 每次修改先读取最新记录，再仅更新选中角色；浏览器支持 Web Locks 时，状态保存和导入使用同名独占锁 |
| 旧角色目录自动纠正较新目录的星导状态 | 旧标签页可能把有效星导记录永久降为拥有 | 加载仅调整合法显示并提示，保留原始星导记录；修改其他角色也不降级该记录 |
| 排队保存或导入在关闭弹窗后仍继续 | 取消操作后仍可能写入 | 关闭弹窗中止排队，执行前再次检查弹窗是否打开 |
| 排队的旧 storage 事件带旧值 | 页面可能短暂恢复到过期记录 | 收到事件时重新读取当前存储值；读取、解析或保存失败时阻止覆盖并保留可恢复数据 |
| 增量更新无法发现仅详情字段变化 | 说明、其他形态等可能继续使用旧快照 | 增加 `--full-details` 供手动完整更新；原增量模式保留 |
| 相同 URL 的图片更新未刷新备份 | CDN 与图片导出可能呈现不同版本 | 增加 `--refresh-images` 供手动刷新全部备份；把图鉴动态卡片使用的图片加入下载集合 |
| 图鉴仅使用仓库目录 | 原站新增角色后，图鉴需等手动部署才能看到 | 图鉴读取两组原站数据并整批校验、合并，失败整批回退；不修改持有记录 |

无 Web Locks 的旧浏览器使用“写前读取最新记录”的兼容回退，可防止顺序覆盖，但 localStorage 本身不提供真正同时写入的事务保证。确认导入仍按预览覆盖全部记录，这是用户明确选择的行为。

## 数据更新链路

访问时的数据加载与仓库静态副本更新需要分别判断。历史核对确认：

- `6bb6697` 之前，榜单及详情直接查询原站 `/v1/characters` API，查询缓存为 180 秒。
- 已有提交 `6bb6697` 引入同源角色快照优先、失败再请求原站 API。本次图鉴之前，当前仓库已采用该策略。按用户最终要求，本次恢复原站数据优先；请求、解析失败或超过 10 秒时读取同源快照，并保留原有 180 秒查询缓存。
- 图鉴每次打开时并行读取梦见、配布两组原站 API 数据，整批验证后按原榜单规则排序合并；任一组失败或超时则整批读取 `data/collection.json`，不会混用一组新数据与一组旧数据。静态目录也进行结构及内容版本校验。
- 新旧目录都按 `slug` 关联个人状态。新增角色、新开放星导或排序变更不依赖手工维护角色名单。已有中文翻译继续应用，新角色无译名时显示原名。

仓库中的静态副本按需手动更新：

```sh
python3 scripts/refresh-rankings.py --full-details --refresh-images
```

该命令获取原站、校验源数据、重施汉化和导航、生成角色快照与图鉴、刷新图片并完成一致性检查。GitHub Pages 和 Cloudflare 保持既有部署方式。整个本地脚本链并非全仓事务；失败后可能留有未发布的本地生成文件，应解决错误并通过检查后再提交。
